## 1. What this area is

The brand-side trade-spend / promotional workspace: Approved Promotions (standard promotions with events and brand-approved fees, EDLP-only promotions, and the Simple Entries grid), the Promotional Calendar (promos-at-a-glance reads, event/submission status writes, and promo notes), and the Monthly Report (a materialized snapshot with export, backfill and an actuals CSV import). Primary users are brand owners and brand sub-users working inside a brand workspace; brokers touch the same data only through their own BrokersController endpoints (promotional-management events/status and the promos-at-a-glance notes reads — covered in workbook 01 §4.1, cross-reference only). Data lives in the `TradeSpend` schema (`TradeSpendPromos`, `TradeSpendPromoEvents`, `TradeSpendPromoNotes`, `BrandApprovedPromotionFees`, `BrandApprovedMonthlyReport` — mapped in `caboodle\src\Modules\Shared\Modules.Shared.Infrastructure\Persistence\MainDbContext.cs:327-341`), everything keyed by `BrandID`. Not a single action on this controller carries an authorization attribute (architecture doc §8-13 lists "TradeSpends (48)"): the `BrandID` header plus `BrandValidationMiddleware` is the whole story today.

## 3. Module catalog mapping

Brand audience (Section B):
- `approved-promotions` (parent `promotion-planning`; Required dep `product-spec`; the catalog's only AutoEnable edge → `trade-spend-sandbox`) — FE routes `promo-planning` **and** `simple-entries` (CS-1708: Simple Entries have no module of their own and write into `POST api/v1/tradespends`). Gates the core promo CRUD, EDLP, duplicate, events, fees and the simple/* rows.
- `promotional-calendar-view` (parent `promotional-calendar`; Required dep `approved-promotions`, OptionalDataSource `regions`) — FE route `promotional-calendar`. Gates the promos-at-a-glance calendar reads, exports, the events-with-same-name drill-down and the status writes (Q1).
- `promotional-calendar-notes` (parent `promotional-calendar`; Required dep `approved-promotions`) — FE route `promotional-notes`. Gates the promo-notes CRUD + export-for-brand.
- `monthly-report` (parent `enhanced-reporting`; Required deps `approved-promotions`, `trade-spend-sandbox`, `product-spec`, `distributors`) — FE route `monthly-report`. Gates all monthly-report rows.
- `trade-spend-sandbox` — gates only `POST {id}/push-to-sandbox` here (Q2); the sandbox module itself is workbook 03.

Broker audience: **none of this controller's rows get a broker slug.** Broker access to this data goes through `BrokersController` (promotional-management events/status, promos-at-a-glance notes — workbook 01). The Broker-audience copy of `approved-promotions` (sort 104) stays what it is today: a dependency anchor for `promotional-management-events`/`-notes`, not a licence to call `/tradespends/*` directly (Q3, D1).

**Gaps:** none structural — every action maps to an existing catalog slug; the judgment calls are which slug (Q1, Q2) and whether brokers keep their incidental direct access (Q3).

**D9 note:** this whole area is downstream of D9. Today a brand owner whose brand has any broker loses the FE entry point via `canAccessTradespend` (§5), but the backend never enforces it. Under D9 the rule is dropped and "does this brand have trade spend" is simply whether the Platform Admin enabled `approved-promotions` (and its children) for the Brand organization — the seeding/backfill must grant it to every brand that uses trade spend today, brokered or not. The `canAccessTradespend` field itself is owned by IAM plan Phase 4.5 (emitted from the entitlement), not by this workbook.

## 5. Parity notes

**What each mechanism actually allows/denies today:**

- **No attributes anywhere.** All 48 actions rely on the global `MapControllers().RequireAuthorization()`; `[BrandIDHeader]` is OpenAPI decoration (`BB\Infrastructure\OpenApi\BrandIdHeaderAttribute.cs:8-14`). No role or permission claim is ever consulted — brand roles have no seeded claims, which is exactly why this controller is attribute-free (IAM plan §2.3).
- **`CurrentUserMiddleware`** parses the `BrandID` header into `CurrentUser.SetBrandID` (`BB\Infrastructure\Auth\CurrentUserMiddleware.cs:18-23`). With no (or an invalid) header, `GetBrandID()` returns `Guid.Empty` (`BB\Infrastructure\Auth\CurrentUser.cs:10,20`) — reads scope to nothing, and the create paths (`POST`, `POST edlp`, `POST simple`, notes upsert) would stamp `BrandID = Guid.Empty` orphan rows.
- **`BrandValidationMiddleware`** (`BB\Infrastructure\Middleware\BrandValidationMiddleware.cs`) is the only gate, and only when the header exists (`:37-38`; headerless requests pass straight through, `:74-77`). ADMIN bypasses (`:48-49`); brokers and sub-brokers pass for any brand in **their own** `BrandBrokers` rows (`:50-51,85-94`); brand owners via `Brands.UserID` (`:54-55,97-104`); brand sub-users via `BrandSubUsers` (`:52-53,106-112`); otherwise 403 (`:63`). So today's effective audience for every row is *anyone connected to the brand, brokers included* — the FE never makes broker calls here, but the server allows them (Q3). Invalid-GUID header writes a 400 body with HTTP 200 (`:66-72`).
- **Handler row guards** are the only per-row defence: promo loads check `BrandID` + `Deleted` (`GetTradeSpendPromoRequest.cs:55`, `UpsertTradeSpendPromoRequest.cs:96`, `UpdateTradeSpendPromoRequest.cs:60`, `DuplicateTradeSpendRequest.cs:120`, `PushPromotionToSandboxRequest.cs:59`, `SimplePromotionGuard.cs:16-27`, `GetBrandApprovedPromotionFeeRequest.cs:57-60`, `UpsertPromoAtaGlanceNoteRequest.cs:57`); list/report queries parameterize `BrandID`. The gaps are the four do-not-reproduce writes below.
- **Job ownership:** promos-at-a-glance export status = ModuleType + `BrandID` + `CreatedBy`, 403 otherwise (`GetPromosAtAGlanceExportStatusRequest.cs:44-49`); monthly-report import jobs = `BrandID` only (`GetMonthlyReportActualImportJobStatusRequest.cs:42-45`, `UploadChunk…cs:93`); monthly-report export jobs stamped `BrandID`+`CreatedBy` at start (`StartExportRequest.cs:53-69`), ownership enforced by the ExportController status route (cross-reference).
- **`CanAccessTradespend` is FE-only.** Computed in `GetMyAssignedBrandsRequest` (`caboodle\src\Modules\Brand\Modules.Brand.Application\Requests\Brands\GetMyAssignedBrandsRequest.cs:334-355`): a brand owner gets `FALSE` if any non-deleted `BrandBrokers` row exists for the brand — with a hardcoded exception, `'Zucchini Beanie Demo Brand'` is always `TRUE` (`:340-347`); brokers/sub-brokers are hardcoded `TRUE` (`:60` region). **No endpoint on this controller checks it** — a brokered brand's owner can call everything today by URL. Dropping the rule (D9) therefore changes nothing server-side here; the rule's replacement (entitlement-driven `canAccessTradespend` in the legacy `/brands/me` contract) is IAM plan Phase 4.5's job.

**Resolver must-match list** (comparator, Phase 2.5): for brand owners and brand sub-users, `BrandsWith(slug, action)` over the four slugs must contain exactly their own brand(s) — owners via `brand-admin` memberships, sub-users via `brand-member` + `BrandAccess(Full)` (§10.1), with every action (D2). ADMIN maps to the support context. The middleware's broker pass-through has no resolver equivalent by design (Q3 tightening below).

**Do-not-reproduce list** (intentional comparator differences, one line each):

1. `PUT {promoID}/events/{id}` checks only event↔promo linkage, never the brand (`UpdateTradeSpendPromoEventRequest.cs:106-110`) — cross-brand event edit for any authenticated user; fail-open.
2. `POST edlp` update path checks `null/Deleted` but not `BrandID` (`UpsertEDLPOnlyPromotionRequest.cs:88-93`) — cross-brand EDLP promo edit; fail-open.
3. `DELETE {promoID}` brand-checks the parent promo but soft-deletes the posted `EventIDs` unscoped (`DeleteTradeSpendPromoEventsRequest.cs:52-53`, `DapperQueryBuilder.cs:64-71`) — any event id deletable behind any owned promo.

## 9. Open questions

1. **Q1 — Which slug gates the promos-at-a-glance status writes** (`PATCH event-status`, `PATCH submission-status`)? They mutate `TradeSpendPromoEvents` (approved-promotions data) but live on the Promotional Calendar screen, as the brand twins of the broker promotional-management writes (01 §4.1). Recommendation: `promotional-calendar-view` with `Edit` — it matches the screen the FE gates, and its Required dependency on `approved-promotions` keeps the data model honest. Alternative: `approved-promotions, Edit` (data-centric), which would let calendar-only users see but never work the calendar.
2. **Q2 — `POST {id}/push-to-sandbox` slug**: it reads an approved promotion but writes sandbox rows. Recommendation: `RM(brand: "trade-spend-sandbox", Create)` — the write lands in sandbox data, and the catalog's AutoEnable edge (`approved-promotions` → `trade-spend-sandbox`) preserves parity for every brand enabled the normal way; a Custom grant without the sandbox module correctly loses the button. Must be decided symmetrically with the sandbox controller's `push-to-tradespend` (workbook 03).
3. **Q3 — Do brokers keep direct access to `/tradespends/*`?** Today the middleware lets any connected broker call all 48 rows; no FE path does. Recommendation: omit the broker audience from every row (tighten; comparator whitelist §5 #7) — broker reads/writes over this data stay on their BrokersController twins per D1's catalog split. Alternative, if product wants read parity: name `broker: "approved-promotions"` (the sort-104 copy) on the read rows only.
4. **Q4 — Is `POST monthly-report/backfill` a brand feature or an ops surface?** The web FE calls it (`monthlyReport.service.ts`), but it takes an arbitrary body `BrandID` today. Recommendation: keep it brand-facing, gate `RM(brand: "monthly-report", Edit)` and derive the brand from the active brand; if Platform-Admin says it is really an ops backfill, move it behind `[MustHavePermission]` instead.
5. **Q5 — Action for `GET monthly-report/refresh`**: it rewrites the brand's materialized snapshot, but it is how the screen gets fresh data (called on page load). Recommendation: `View` — it writes only derived rows for the caller's own brand, and `Edit` would break read-only (Custom View) grants' screens. Needs sign-off because it bends the "writes → Edit" mapping.
6. **Q6 — Notes deletion is a hard delete** (`DeletePromoAtaGlanceNotesRequest` uses `HardDelete` while the rest of the area soft-deletes). The scope fix is in §6 regardless; should the delete also become soft for audit/purge symmetry? Recommendation: yes, align to soft delete (`DapperQueryBuilder.Delete`) when adding the brand scope.
7. **Q7 — Retire `GET promos-at-a-glance/events/filters`?** Superseded by `POST promos-at-a-glance/filters` (CS-1552; the FE comment says so explicitly). Recommendation: guard it identically now (`promotional-calendar-view`, View), confirm zero callers after the FE migration, retire in Phase 5.
