## 1. What this area is

The file repository: a two-sided file explorer (folders, uploads incl. chunked multipart, downloads via presigned S3 URLs, rename/move/delete, anonymous share links). The **brand area** is the "Files" screen inside a brand workspace (`/{brandID}/file-upload`), used by brand owners/sub-users and by brokers working on that brand; it has a Public and an owner-only Private sub-repository (`PrivacyType`). The **broker area** (`/file-repository`) is the brokerage's own repository with no brand at all — every route is duplicated as a `broker/...` twin sending the *same* request type, and the handler decides the area from the caller's role + header, not from the route. Data lives in `FileRepository.FileDirectories`, `FileRepository.UserFiles` and `FileRepository.FileShareLinks` (`MainDbContext.cs:344-359`), with blobs in S3 under `CaboodleFiles/{BrandID}/…` (brand) or `CaboodleFiles/Broker/{brokerUserID}/…` (broker) (`BB\Core\Application\Common\Models\Constants.cs:16-17`). Not one action in the area carries a permission attribute except the anonymous `ShareController`; all authorization is handler role checks via `IUserService.GetRolesAsync` — which is why §5 is the heart of this workbook.

## 3. Module catalog mapping

`files` exists in **both audiences** with different IDs (Section B): Brand `files` (root module, FE route `file-upload`), Broker `files` (root module, FE route `file-repository`). No children, no dependencies, no data-source copies involved. Every non-anonymous action in this area maps to one of the two `files` modules — dual-audience rows name both in one attribute (D1: a broker in a brand workspace uses the *Brokerage's* `files` entitlement applied to the active brand).

**Gaps:** none needing new slugs.
- The `broker/...` route twins are broker-workspace-only → `RM(broker: "files", …)`, brand-independent (no active `BrandID`; template convention / invariant 11 mechanism).
- `GET /share/{token}` is a public capability-token endpoint → `[AllowAnonymous]`, justified in §4.3 Notes.
- `POST files/share` / `DELETE files/share/{token}` exist only for the brand area today (the FE comment says so explicitly, `caboodle.web\src\service\file-explorer.service.ts:60-73`); whether the broker repository gains share links is Q3, not a slug gap.

## 5. Parity notes

**What each mechanism actually allows/denies today:**

- **No permission attributes anywhere** (ShareController's `[AllowAnonymous]` aside): the outer gate is the global `RequireAuthorization` plus `BrandValidationMiddleware` *only when a `BrandID` header is present* (`BB\Infrastructure\Middleware\BrandValidationMiddleware.cs`: ADMIN bypass `:48-49`; brokers via their own `BrandBrokers` rows `:85-95`; brand owners via `Brands.UserID` `:97-104`; brand sub-users via `BrandSubUsers` `:106-112`; else 403 `:60-63`; invalid-GUID 200-status bug `:66-72`). The `broker/...` twins are called headerless, so for them the middleware never runs — role + header-absence **is** the authorization.
- **AreaResolution** (repeated in 10 handlers, e.g. `GetRootDirectoryTreeRequest.cs:56-58`): roles come from the user store via `IUserService.GetRolesAsync`, not the JWT; `brandID = (BROKER|BROKERSUBUSER) && header empty ? null : header`. BROKERSUBUSER in the broker area acts as the parent broker (`SharedDataService.cs:534-546` — throws 404 if the sub-broker has no `BrandBrokers` row). A brand-role user calling a `broker/...` twin lands in the *brand* branch with `brandID = Guid.Empty` → empty results, not 403.
- **Privacy (`PrivacyType`)**: Private root read and Private upload are BRANDOWNER-only in brand context (`GetRootDirectoryTreeRequest.cs:60-67`, `UploadFileRequest.cs:99-104`, `UploadChunkFileRequest.cs:103-106`); the broker area's Private is primary-BROKER-only (sub-broker denials at `GetRootDirectoryTreeRequest.cs:75-78`, `UploadFileRequest.cs:87-93`, `DirectoryTreeCreationRequest.cs:85-91`). Enforcement is scattered: directory creation checks nothing (`DirectoryCreationRequest.cs` has no Private check), tree-creation silently drops the root's PrivacyType, and none of the by-ID reads/downloads re-check privacy. Errors are 400 validator throws, not 403.
- **Scoped specs** (the correct pattern, used by root reads and the share/rename/broker-mutation paths): `GetFileDirectoryOfBrandUserSpec`/`GetFileOfBrandUserSpec` (BrandID), `GetDirectoriesOfBrokerSpec`/`GetFileofBrokerUserSpec` (`UserId` + `BrandID IS NULL`), `GetFileOfBrandByIDSpec` (BrandID + id), `GetFileByUserIDSpec` (owner + null-brand + id) — all in `MFA\Specifications\`.
- **Unscoped loads** (the gap): `GetFileDirectorySpec(id[, privacy])` filters nothing tenant-shaped, and `GetDirectoryRequest`/`GetDirectoryTreeRequest`/`GetParentDirectoryRequest`/`FileDownloadRequest` query by bare ID. The S3 side of mutations always derives its base path from the *caller*, so a cross-tenant DB hit pairs with a wrong-tenant (usually no-op) S3 operation — DB and blob state diverge.

**Resolver must-match list** (comparator, Phase 2.5): broker-area owner resolution (BROKER → self, BROKERSUBUSER → parent) must equal the migrated Brokerage `OrganizationID` for every broker user; brand-area membership (middleware) must equal `BrandsWith("files", action)` containing the header brand; the share trio's behavior — scoped create (`CreateFileShareLinkRequest.cs:135-161`), Private refusal (`:84-89`), active-link reuse (`:91-93`), accessibility-gated revoke (`RevokeFileShareLinkRequest.cs:74,100-122`), and every resolve-time re-check in §4.3 — must match exactly; `UpdateFileRequest`'s brand scoping (`:131-138`) is the reference for what the other brand mutations should have done.

**Do-not-reproduce list** (intentional comparator differences, one line each):

1. `GET /directory`, `GET /directory/tree`, `GET /directory/parent` — unscoped by-ID reads of any tenant's tree (`GetDirectoryRequest.cs:118-142`, `GetDirectoryTreeRequest.cs:78-84`, `GetParentDirectoryRequest.cs:45-58`); fail-open.
2. `GET /directory/search` — `brandID` taken from the query string and never checked against the caller (`GetDirectoriesAndFilesByNameRequest.cs:79-83`); cross-tenant read incl. Private; fail-open.
3. `DELETE /directory` — no ownership check before a recursive **hard** delete of rows (`DeleteDirectoryRequest.cs:88-113`) and an S3 prefix delete rooted at the caller's path (`:76-81`); fail-open and destructive.
4. `PUT /directory` — unscoped directory + parent loads let any user rename/move any tenant's folder (`DirectoryUpdateRequest.cs:86-103`); fail-open.
5. `GET /directory/download` — unscoped load, no privacy check: zips a Private tree for users the root read denies (`DirectoryDownloadRequest.cs:90-96`); fail-open.
6. `GET /files/download` — no check at all; presigned URL for any file id (`FileDownloadRequest.cs:45-68`); fail-open.
7. `DELETE /files/{id}` and `PUT /files/move` brand paths — the SQL binds `@BrandID` but the `WHERE` clause omits it (`DeleteFileRequest.cs:135-147`, `FileMoveRequest.cs:162-174`), and move's destination directory is loaded unscoped (`FileMoveRequest.cs:132-141`); dead filter, fail-open.
8. `POST /files/upload/chunk` — client-supplied `Key`/`UploadId` continue a multipart upload at an arbitrary bucket path (`UploadChunkFileRequest.cs:125-135`); target validates the session server-side.
9. `DirectoryTreeCreationRequest` root row never gets the requested `PrivacyType` (insert `:93-105`), so "upload folder as Private" lands Public; reproduce the *intent*, not the bug.
10. Directory creation performs no Private role check and validates the parent by id+privacy only (`DirectoryCreationRequest.cs:71-78`); the dup-name check runs against the sub-user's id instead of the parent broker's (`:82,108-136`); all three are bugs, not contracts.
11. Validator-style 400s where authorization fails (Private denials, invalid parent) — the new model answers 403 per the plan §5-2 contract; comparator whitelists the status change.
12. `BrandValidationMiddleware` invalid-GUID 200-status bug (`:66-72`) — reproduce the 400.

## 9. Open questions

1. **Q1 — What does the Private repository become?** Today it is role-gated, inconsistently: brand Private = BRANDOWNER only (read root + upload; directory-create forgot the check, directory-download bypasses it), broker Private = primary BROKER only, and the FE shows brand sub-users a Private tab the BE rejects. The new model has no "owner" — D2 even starts members at Full. Recommendation: keep `PrivacyType` and gate Private on the **org-admin role** (brand-admin / brokerage-admin) in the resolver context, enforced uniformly on read, create, upload, download and share; fix the FE tab to match. Alternative (bigger): retire Private or make it per-user personal space. Needs product sign-off.
2. **Q2 — Confirm `UserId` as the tenancy key for broker-area rows** (`FileDirectories`/`UserFiles` with `BrandID IS NULL`). It already holds the primary broker's user id = the future `BrokerageOrganizationID` (§10.1 id-reuse), and the S3 prefix `CaboodleFiles/Broker/{id}` matches, so **no new column** — but these tables are not in invariant 11's list, so Platform-Admin confirmation is needed that no backfill beyond the Phase 1.5 reconciliation report is required (verify no broker-area rows carry a sub-broker's id from before the parent-stamping convention; rename the column in Phase 5 alongside `PromoTabs.BrokerID`).
3. **Q3 — Share-link hardening and reach.** (a) Links default to *never expiring* (null `ExpiresOn`, cap 3650 days when set) — recommend a default expiry (e.g. 90 days) with "never" as an explicit choice; comparator whitelists the tightening. (b) `/share/*` has no rate limiting — fold into the IAM plan 0.4 rate-limit middleware (defense in depth; the 256-bit token already resists enumeration). (c) The broker repository has no share capability (FE deliberately; no broker route) — decide whether broker `files` gains it (recommendation: yes, same handler, org-scoped file lookup) or stays download-URL-copy only.
4. **Q4 — Collapse the `broker/...` route twins after cut-over?** They exist only because audience is derived from role+header today; once `[RequireModule]` + the workspace header decide the area, one route per operation suffices. Recommendation: keep both through Phase 4 for parity, collapse in Phase 5 when the FEs move to `/me/access` (the FE services already split cleanly, so it is a mechanical URL change).
