## 1. What this area is

The brand-workspace Trade Spend Sandbox: draft promotions organized as **promotion families** holding up to five **versions** (`VersionNumber`, `ParentVersionID` lineage), each version owning its promotional events and promotion fees. One version per family can be **pushed** into Brand Approved (the TradeSpend module's `TradeSpendPromos`), and exactly one feeds reporting (`ReportingVersionID`); the versions list computes `isOutOfDate` by comparing pushable content changes against `PushedOn` (`MTSA\Requests\GetPromotionVersionsRequest.cs:96-127`). Users are the brand workspace's occupants — brand owners/sub-users *or* broker users working a connected brand (today the `CanAccessTradespend` rule hands the toolset to the brokerage when one exists; decision D9 retires that). Data lives in the `TradeSpendSandbox` schema: `PromotionFamilies`, `Promotions`, `PromotionalEvents`, `PromotionFees`, plus the `SandboxMonthlyReport` snapshot (`MSI\Persistence\MainDbContext.cs:483-505`), with the push path writing the brand-owned `TradeSpend` schema through `ISharedDataService` (`MSI\Services\SharedDataService\SharedDataService.cs:842-994`).

Cross-module readers (other workbooks): ReportsController `POST roll-up/sandbox-promotions` and DashboardController `GET roll-up-report` read sandbox promotions; TradeSpendsController's monthly-report endpoints read `SandboxMonthlyReport`; TradeSpendsController `POST {id}/push-to-sandbox` is the reverse path.

## 2. Data ownership

Unlike workbook 01's tables, nothing here carries a broker/brokerage column and nothing scopes by `CreatedBy` or `BrandBrokers` — every read and write filters on `BrandID` = the header brand. Architecture invariant 10 lists "promotions, trade spend" as brand-owned and invariant 11 does **not** list these tables, so they are classed Brand-owned — but because both the brand's users and *every* connected brokerage's users share one draft space per brand, that classification needs explicit sign-off (Q1).

## 5. Parity notes

**What each mechanism actually allows/denies today:**

- **There is no claim gate at all.** Zero `[MustHavePermission]` attributes means the controller never consults role claims — which is precisely why BRANDOWNER/BRANDSUBUSER (no seeded claims, `BB\Infrastructure\Persistence\Initialization\ApplicationDbSeeder.cs:52-58`) can use it. Any signed-in user of any role reaches the handlers; the only outer gate is the brand header.
- **`BrandValidationMiddleware`** (`BB\Infrastructure\Middleware\BrandValidationMiddleware.cs`) runs on all 26 actions because all carry `[BrandIDHeader]` and the FE always sends the header. ADMIN bypasses (`:48-49`); brokers/sub-brokers pass if the brand ∈ their own `BrandBrokers` rows (`:85-95`); brand owners via `Brands.UserID` (`:97-104`); brand sub-users via `BrandSubUsers` (`:106-112`). So **a broker user is admitted to any connected brand's sandbox today** — rows are shared brand-wide across brokerages (Q1). Known bug: invalid-GUID header writes a 400 body with HTTP 200 (`:66-72`).
- **Missing header:** the middleware only runs when a header is present; `ICurrentUser.GetBrandID()` then returns `Guid.Empty` (`BB\Infrastructure\Auth\CurrentUser.cs:10,20`, set by `CurrentUserMiddleware.cs:22`), so brand-scoped queries return nothing / 404 — benign. The two unscoped event endpoints (`GET/PUT {promoID}/events/{id}`) don't filter by brand at all, so for them a missing header changes nothing: they are reachable **headerless** by any authenticated user.
- **Handler scoping** is otherwise uniform: load row → 404 unless `row.BrandID == GetBrandID()` (and parent-id match for versions/fees/events). `MarkFamilyAsPushedAsync` (`SharedDataService.cs:1050-1069`) does not re-check the brand but is only called after the push handler's check.
- **`CanAccessTradespend` is FE-only.** `GET /brands/me` computes it as "false if any live `BrandBrokers` row exists, with a hard-coded exception for the 'Zucchini Beanie Demo Brand'" (`caboodle\src\Modules\Brand\Modules.Brand.Application\Requests\Brands\GetMyAssignedBrandsRequest.cs:339-347`). No sandbox endpoint reads it, so a brand owner whose menu hides Promo Planning can still call every endpoint here directly. D9 drops the rule; parity for the comparator is "endpoint behavior never depended on it".

**Resolver must-match list** (comparator, plan 2.5): for every persona, access to each action must equal *middleware admit* ∧ *row.BrandID = header*. Concretely: brand-admin/member of brand B → allowed on B's rows; broker/sub-broker of a brokerage connected to B → allowed on B's rows (today — the module grant becomes the new discriminator); unconnected broker, other brand's users → 403/404. `BrandsWith` is never needed here: there is no cross-brand mode — every action is single-brand via the header.

**Do-not-reproduce list** (intentional comparator differences):

1. `GET {promoID}/events/{id}` reads any brand's event by GUID — handler has no brand filter and ignores `promoID` (`GetPromotionalEventRequest.cs:41-56,128-130`); fail-open, fix with a brand + promotion check.
2. `PUT {promoID}/events/{id}` writes any brand's event by GUID — only `PromotionID == promoID` is checked and both are caller-supplied (`UpdatePromotionalEventRequest.cs:110-114`); fail-open, violates invariant 10's `BrandID` keying.
3. `GET name-exist?familyId=…` is a cross-brand version-name oracle — `IsVersionNameExistAsync` never brand-checks the family (`CheckPromotionNameAlreadyExistRequest.cs:64-67`, `PromotionDTOBuilder.cs:50-74`); fix by validating the family's brand.
4. `BrandValidationMiddleware` invalid-GUID 200-status bug (shared with workbook 01) — reproduce the 400, not the 200.
5. The duplicate `PATCH {id}/events/update-status` route — dead spelling the FE never calls; retire rather than carry two identical guards (Q3).

## 6. Code changes beyond attributes

**Queries to re-scope:** none — Brand-owned data, `BrandID` filters already in place (Q1). The three fixes above are scoping *additions inside this brand*, not tenancy changes: add `BrandID == header` (+ `PromotionID == promoID`) to `GetPromotionalEventRequest` and `UpdatePromotionalEventRequest`, and a family brand check to the `name-exist` version branch. Ship these with (or before) Phase 4.2 — they are live cross-brand holes regardless of the IAM timeline.

**Helpers/files to delete at Phase 4.4:** none module-specific — this area has no access helper; it leans entirely on the shared `BrandValidationMiddleware`, retired once every consumer area has cut over (workbook 01 §6 owns that list). After the cut-over, `[RequireModule]`'s active-brand validation replaces the middleware for all 26 actions.

**Demand() call sites (payload-dependent):**
- `UpsertPromotionRequest` and `UpsertEDLPOnlyPromotionRequest`: `request.ID is null ? Create : Edit` (both payloads carry `Guid? ID`).
- `PushPromotionToTradeSpendRequest`: cross-module `_access.Demand("approved-promotions", family.PushedVersionID is null ? Create : Edit)` — pending Q2.
- `DeletePromotionsRequest`: cross-module `_access.Demand("approved-promotions", Delete)` only when the families have BAP copies — pending Q2.

**BrandID-header edge cases:** every action is single-brand; none runs in cross-brand allowlist mode, so a missing header is simply a 403 under `[RequireModule]` (in a Brand workspace the header defaults to the organization id, architecture §6.1 — today's brand-workspace FE always sends it). A **stale** header for a brand the caller can no longer reach must 403, not sign out (plan §5-2: 403-never-401). Brokerage-workspace callers must send the brand header explicitly; the attribute checks the slug against that active brand. The two currently-unscoped event endpoints are the only rows where the middleware is doing *zero* effective work today — their handler fixes must land in the same deploy that retires it, or they go from "cross-brand" to "cross-brand and anonymous-role" exposure.

**Transactions:** the push path is four sequential writes with no enclosing transaction (`CreateTradeSpendPromotionAsync` → bulk event replace → bulk fee replace → `MarkFamilyAsPushedAsync`) — a failure mid-push leaves Brand Approved holding a promo with stale/no events while the family still looks unpushed; same shape for `DeletePromotionsRequest` (sandbox Dapper batch, then BAP deletes, then snapshot refresh). Worth wrapping when the Demand() edits touch these handlers anyway. `DeletePromotionVersionRequest`'s cascade is a single multi-statement Dapper command (one implicit transaction) — fine.

## 9. Open questions

1. **Q1 — Ownership sign-off: are sandbox drafts brand-shared or brokerage-private?** All five tables are `BrandID`-keyed with no brokerage column; the brand's users and every connected brokerage share one draft space, one per-brand name namespace, and one Brand Approved copy per family. Invariant 10 ("promotions, trade spend" = brand-owned) supports keeping that; invariant 11 doesn't list these tables. The old `CanAccessTradespend` rule masked the collision by letting only one side hold trade spend — D9 removes the mask, so brand + brokerage (or two brokerages) can now draft simultaneously. Recommendation: **Brand-owned, no `BrokerageOrganizationID`** — shared drafts match the single-BAP-copy push model; if the Platform Admin instead wants D6-style privacy here, it is a redesign (org column on four tables, per-org name uniqueness, per-org family→BAP mapping), not a Phase 1.3 line item.
2. **Q2 — Should push/delete demand the `approved-promotions` module?** Push materializes rows in `TradeSpend.TradeSpendPromos` (+events/fees) and family delete removes them; a tenant entitled to `trade-spend-sandbox` alone could otherwise write/delete Brand Approved data it cannot see. Recommendation: yes — handler `_access.Demand("approved-promotions", Create/Edit)` on push and `Demand("approved-promotions", Delete)` on the BAP cascade. The AutoEnable edge (`approved-promotions` → `trade-spend-sandbox`) means the common case is unaffected; only sandbox-without-BAP tenants newly 403.
3. **Q3 — Retire the duplicate event-status route.** `PATCH {id}/events/update-status` and `PATCH {id}/update-event-status` dispatch the same `UpdateEventsStatusRequest`; the FE calls only the latter (`promo.service.ts:813`). Recommendation: delete the former in Phase 4.2 (shrinks the reflection baseline); otherwise both must carry identical guards and tests forever.
4. **Q4 — Confirm the broker audience on the attribute.** The Broker-audience `trade-spend-sandbox` copy (sort 105) is today only a dependency anchor for `promotional-management-events`, yet broker users demonstrably work brand sandboxes (middleware admits them; `CanAccessTradespend` exists precisely to hand them the toolset). Recommendation: keep `broker: "trade-spend-sandbox"` in every row as written (D1: the Brokerage's catalog applied to the brand's data), and let the Platform Admin control it per-brokerage via the entitlement; dropping the broker side would lock brokers out of brokered brands' promo planning at cut-over — a regression D9 does not ask for.
5. **Q5 — Production reveal of the sandbox.** In production the FE shows the sandbox only to the `BRAND_TO_IGNORE` whitelist (staging shows all); the catalog, not a code whitelist, should decide this post-IAM. Recommendation: Platform Admin confirms which brands get the `trade-spend-sandbox` assignment at backfill time (whitelist members at minimum — plus every brand with `approved-promotions`, per the AutoEnable edge), then the FE flags are deleted; sequence before `ALLOW_ALL_WHEN_NO_MODULES` flips.
