## 1. What this area is

The broker-workspace screens: Market Overview, Category Review + Category Review Calendar, Brand Report, Promotional Management (events read/status over brand trade-spend data, plus the promos-at-a-glance notes read), the Promotional Management Notes tab grid (PromoTabs), and Distributor APL / Retail APL. Primary users are brokerage users (BROKER / BROKERSUBUSER roles today); four Market Overview endpoints and a handful of Category Review / Brand Report endpoints are brand-side twins called from the brand workspace. Data lives in the `Broker` schema (`MarketOverviews`, `CategoryReviews`, `CategoryReviewCalenders` + `CategoryReviewCalenderDateAssignments`, `BrandReports` + `BrandReportEmailLogs` + `BrandReportStatusOptions`/`BrandReportStatusSettings`, `CategoryReviewEmailLoggers`, `PromoTabs`/`PromoTabColumns`/`PromoTabRows`/`PromoTabCells`, `DistributorAPLs`), with reads into `TradeSpend.TradeSpendPromoEvents`/promo notes and heavy scoping through the legacy `Brand.BrandBrokers` table.

## 3. Module catalog mapping

Broker audience (Section B): `market-overview`; `promotional-management` → children `promotional-management-events`, `promotional-management-notes`; `category-review-group` → children `category-review`, `category-review-calendar`; `distributor-apl` (nav also gates `/retail-apl` on it); plus the data-source copies (sort 100–105), of which `approved-promotions` is the Required dependency of both promotional-management children.

Brand-audience twins used by this area's brand-side endpoints: `category-review`, `category-review-calendar` (under `category-review-report`), `broker-market-activities` (under `reports`). Slugs `category-review`/`category-review-calendar` exist in **both** audiences with different IDs — the dual-audience rows below name both in one attribute.

**Gaps:**
- **Brand Report has no catalog slug in either audience**, and the broker FE route `/brand-report` is neither in `BROKER_ROUTE_MODULES` nor in the nav. Proposal (Q1): new Broker-audience module `brand-report`, parent `category-review-group`, dependency `category-review` (Required) — reports are generated from category reviews. Matrix rows below use `broker: "brand-report"` marked *(Q1)*.
- `GET /brokers` (admin broker list) — no slug; **superseded by IAM plan** (§10.1: broker users → Organizations; `BrandBrokers` → BrandConnections/BrandAccess; admin reads move to `OrganizationsController` / platform memberships view). No module guard invented.
- `POST category-reviews/all` and `DELETE category-reviews` — admin-app surfaces (handler admin-check / no check). Platform: keep `[MustHavePermission]`, retire in favour of `/bulk` (Q5).
- `GET banner`, `GET {regionID}/get-retailers`, `GET {retailerID}/regions/{regionID}/banners` — global lookups feeding the Market Overview create form → `market-overview`.
- `/retail-apl` — no `retail-apl` module exists (slug commented out in FE); rows ride on `distributor-apl`.

Cross-reference: FE module gating currently reads `GET /brands/me` (out of scope here; IAM plan Phase 4.5 owns its reimplementation). None of this area's endpoints feed it.

## 5. Parity notes

**What each mechanism actually allows/denies today:**

- **Claim seeding is the outer gate for every `MHP(..., Broker)` row.** Only ADMIN, BROKER, BROKERSUBUSER get permission claims (`BB\Infrastructure\Persistence\Initialization\ApplicationDbSeeder.cs:52-58`); brand roles get none, so every MHP row here is 403 for brand users — which is why all brand-side twins are attribute-free. BROKER set = all `CaboodleModule.Broker` permissions minus resource `Brokers` and minus StatusOption/StatusSettings writes; SubBroker additionally loses `BrokerPromoTab.Delete` (`BB\Core\Shared\Authorization\CaboodlePermissions.cs:203-222`).
- **`BrandValidationMiddleware`** (`BB\Infrastructure\Middleware\BrandValidationMiddleware.cs`): runs only when a `BrandID` header is present; ADMIN bypasses (`:48-49`); brokers/sub-brokers pass if the brand is in **their own** `BrandBrokers` rows (`:85-95`); brand owners via `Brands.UserID` (`:97-104`); brand sub-users via `BrandSubUsers` (`:106-112`); otherwise 403 (`:60-63`). Bug: an invalid-GUID header writes a 400 JSON body but never sets the status code → client sees 200 (`:66-72`).
- **`CategoryReviewAccessHelper`** (`MBA\Helper\CategoryReviewAccessHelper.cs`): roles read from the user store, not the JWT; ADMIN short-circuits with full access (`:78-83`). With an explicit brandId: brand-side, 403 unless caller ∈ brand's brokers (incl. parents via `ParentBrokerID`, `:164-187`) ∪ brand users (`:85-97`). Without: side derived from role; broker side builds the broker-company closure — parent broker + all sub-brokers via `BrandBrokers.ParentBrokerID` (`:203-253`) — plus the brand users of its brands (`:255-276`); accessible brand ids = union of the company's `BrandBrokers` brands (`:140-162`).
- **`PromoTabAccessHelper`** (`MBA\Helper\PromoTabAccessHelper.cs`): broker company = caller (BROKER) or parent broker (BROKERSUBUSER, `:72-98`); all other roles 403 (`:82-85`); row access = `tab.BrokerID == company` (`:101-115`); `EnsureBrokerOwner` restricts destructive structure ops to the primary BROKER (`:27-33`).
- **`PromotionalManagementBrandAccess`** (`MBA\PromotionalManagement\PromotionalManagementBrandAccess.cs:11-40`): allowlist = `BrandBrokers.BrandID WHERE BrokerID = caller`; `IntersectWithRequestedBrands` returns the full allowlist when the request names none — exactly the architecture §6.3 pattern, minus module awareness.
- **`BrokerBrandQueryHelper`** (`MBA\MarketOverview\BrokerBrandQueryHelper.cs:25-52`): same allowlist, but **throws** a validation error naming the inaccessible brand ids instead of silently intersecting.

**Resolver must-match list** (comparator, Phase 2.5): for every migrated user, `BrandsWith(slug, action)` must equal today's `BrandBrokers`-derived list — primary broker rows → active `BrandConnections` + brokerage-admin Full; sub-broker rows → `BrandAccess(Full)`; the CategoryReview "brand users of broker" read-reach is reproduced by the brand audience's own grants, not by the brokerage context.

**Do-not-reproduce list** (intentional comparator differences, one line each):

1. `DELETE /brokers/category-reviews` — no check of any kind and a **hard** delete (`DeleteCategoryReviewsRequest.cs:45-48`); fail-open, replaced by platform guard or retirement.
2. `POST /brandreport/analytics/{brandId}` and `POST /brandreport/due-dates` have no attribute and (analytics) no handler check — any authenticated user can read any brand's report KPIs; fail-open.
3. `PUT /brandreport/{id}` + the three notes endpoints scope nothing beyond a 404 — any broker-claim holder can write any brokerage's reports; violates D6.
4. `GetBrandReportAuditLogByUserRequest.cs:60` uses `ICurrentUser.IsInRole(ADMIN)`, which is always false (JWT carries no role claim) — the admin bypass is dead code; replace with the support context, don't port the dead check.
