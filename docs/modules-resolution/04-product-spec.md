## 1. What this area is

The brand's product master data: the Product Spec screens (`/categories`, `/products`, `/pricing` in the brand workspace) that manage product specifications, their categories, and per-distributor price lists. Primary users are brand users; connected brokers can reach the same screens through the brand workspace (and under D1 reach the data through the Broker-audience `product-spec` copy), and the Platform Admin edits it from the admin app via `brandScopedHeaders()`. Data lives in `ProductSpecs.ProductSpecifications`, `ProductSpecs.Categories` and `ProductSpecs.PriceList` (singular), all keyed by a non-null `BrandID`. This catalog is the data source half the platform depends on: price list writes propagate per-unit prices into `TradeSpend.TradeSpendPromoEvents`, product creation spawns `CRM.BannerSKUs` rows, and nine other modules declare catalog dependencies on `product-spec`.

## 3. Module catalog mapping

Brand audience (Section B): root `product-spec` (Product Spec, no FE route) → child `categories-products-pricing` (gates FE routes `categories`, `products`, `pricing`; nav "Management → Product Specs"). Broker audience: the `product-spec` data-source copy (sort 100, no FE route) — the D1 vehicle by which brokers reach this area.

`product-spec` is the catalog's most-depended-on slug. Brand audience: Required for `banner-count-graph`, `trade-spend-roll-up-report`, `approved-promotions`, `trade-spend-roll-up`, `monthly-report`; OptionalDataSource for `retail-reports`, `ask-caboodle`. Broker audience: Required for `market-overview`, `promotional-management-events`, `distributor-apl`. The resolver's Required-dependency rule (arch §6.2 last line) grants **View** on `product-spec` to anyone granted those modules — which is exactly what this area's lookup endpoints need to honour. That is why the matrix gates the API on the **parent** `product-spec` in both audiences, as the architecture's own Upsert example does (§6.3: `_access.Demand("product-spec", …)`), and leaves `categories-products-pricing` as an FE-navigation child (Q1).

**Gaps:**
- The five `for-admin` / `filter-options` rows are admin-app master-data browse screens — Platform: keep `[MustHavePermission]`. Not superseded by IAM (they browse business data, not identity).
- `GET productspecs/for-bannerSku/{bannerID}` is a purpose-built picker for the Banner SKU screens, which the FE gates on `distributors` (brand `banners` route → `distributors`, Section C) — gating it on `product-spec` would 403 Custom users who hold only `distributors`. Proposal (Q5): gate on brand `distributors`.
- The two `export-sample-file` rows return static CSV templates with no brand data → `View` floor, noted per row.
- Admin-app bulk import/export of this data goes through `masterdataupload/productspecs|categories` (MasterDataUploadController, DataUpload area) — cross-reference only, not in this workbook.
- AdminController `GET data-cleanup/sync-per-unit-price` sends `SyncPricingsOfEventsRequest`, which lives in this BE project (`MPA\PriceList\SyncPricingsOfEventsRequest.cs`) — the endpoint belongs to the Admin workbook (platform data-cleanup surface), not here.

## 4. Endpoint authorization matrix

Action mapping per template (§4.3). Every brand-data row below is dual-audience `RM(brand: "product-spec", broker: "product-spec", X)` unless stated — brand users via their own org's modules, brokers via the Broker-audience copy on the active connected brand (D1). ## 5. Parity notes

**What each mechanism actually allows/denies today:**

- **`BrandValidationMiddleware` is the only gate for the 28 attribute-free rows.** Every one carries `[BrandIDHeader]`; the middleware runs only when the header is present and passes brand owners (`Brands.UserID`), brand sub-users (`BrandSubUsers`), brokers/sub-brokers whose `BrandBrokers` rows include the brand, and ADMIN unconditionally (`BB\Infrastructure\Middleware\BrandValidationMiddleware.cs:48-112`). **No role is excluded from any action**: a broker sub-user can call `productspecs/upsert` or the deletes for any connected brand — the FE just hides the buttons (below).
- **Missing header = silent empty scope, not a 403.** `ICurrentUser.GetBrandID()` returns `Guid.Empty` when the header is absent (`BB\Infrastructure\Auth\CurrentUser.cs:20`; the middleware never runs) — reads return empty pages, and creates would stamp `BrandID = Guid.Empty` orphan rows. Target behavior: brand workspace defaults the active brand to the organization id, broker workspace 403s without a brand (arch §6.1).
- **Claim seeding** makes the five `MHP` rows ADMIN-only (`CaboodlePermissions.cs:132-134` live in modules the Broker/SubBroker sets exclude, `:203-221`; brand roles have no claims).
- **Handler scoping**: every read/export/import/upsert filters or validates on `GetBrandID()` (anchors per row in §4); the three deletes, `GET pricelists/{id}` and the link-product product-load do not.
- **FE-only sub-user read-only veneer, no server enforcement**: `caboodle.web` hides add/upload/export buttons, the edit action and row selection (delete) from BRANDSUBUSER **and** BROKERSUBUSER via negative role checks — `src/components/productSpecs/ProductTable.tsx:153,427,465,518`, `PriceListTable.tsx:272,436,470`, `CategoryTable.tsx:115,286,316`. The server accepts their writes regardless. Migrating sub-users at `Full` (arch §10.1: `BrandSubUsers` → `brand-member` + `BrandAccess(Full)`; sub-brokers → `BrandAccess(Full)`) **keeps today's real server-side behavior** — the comparator must baseline against the API, not the UI. If product instead wants the UI intent enforced, that is exactly a `Custom` grant of `product-spec: view` — Q2.
- **Admin app**: all its writes here ride the ADMIN middleware bypass + `brandScopedHeaders()` (`caboodle.admin\src\helper\crmDataUpload.helper.ts:36-43`; call sites `src\services\productSpec.service.ts:95-131`, `priceList.service.ts:86-105`, `category.service.ts:74-93`). Target: support context (§4 header note).

**Resolver must-match list** (comparator, Phase 2.5): for every migrated user and each brand, "module `product-spec` (own audience) with action X on the active brand" must equal today's `BrandValidationMiddleware` verdict: brand owner/sub-user → their own brand only; primary broker → active `BrandConnections` brands at brokerage-admin Full; sub-broker → `BrandAccess(Full)` brands; ADMIN → support context. Since every role passes everything today, disagreements can only come from the do-not-reproduce rows and from `Custom` grants, which have no legacy counterpart.

**Do-not-reproduce list** (intentional comparator differences):

1. `DELETE /productspecs` soft-deletes arbitrary ids with no brand scoping (`DeleteProductsSpecRequest.cs:133-141`); additionally its price-list and APL referential checks are copy-paste duplicates of the BannerSKU query and never run (`:84-118`) — fail-open cross-brand delete; the dead checks are a bug, not a contract.
2. `DELETE /productspecs/force-delete` hard-deletes across 7 tables with no ownership check, deletes `Broker.DistributorAPLs` by **UPC globally** (UPC uniqueness is per-brand, so another brand's same-UPC rows and other brokerages' APL/MarketOverview rows are destroyed), and interpolates values into SQL (`ForceDeleteProductSpecRequest.cs:66-108`). Fail-open and cross-tenant; rewritten, not ported (Q4).
3. `GET /pricelists/{id}` has no BrandID filter (`GetPriceListRequest.cs:41-61`) — cross-brand read by id.
4. `DELETE /pricelists` unscoped (`DeletePriceListsRequest.cs:42`).
5. `PATCH /categories/{id}/link-product` loads products without a brand filter (`GetProductsByBrandIDSpec.cs:13-19`) — cross-brand adoption of an uncategorized product.
6. `DELETE /categories` unscoped (`DeleteCategoriesRequest.cs:138`).
7. Missing-header behavior (empty scope / `Guid.Empty` writes) becomes a 403 or an org-id default per arch §6.1 — reproduce the deny, not the silent empty page.
8. `GET for-bannerSku` loses its (unused) broker reach when gated `brand: "distributors"` only (Q5) — whitelist the broker-persona 403.

## 6. Code changes beyond attributes

- **No query re-scoping**: all stay `BrandID`-keyed (invariant 10). No new column, no backfill (plan 1.3 does not touch this schema).
- **Row guards to add** (the §5 fail-open rows): brand filter in `DeleteProductsSpecRequest` / `DeletePriceListsRequest` / `DeleteCategoriesRequest` (extend `DapperQueryBuilder.Delete` with a `BrandID` predicate or pre-filter ids), `GetPriceListRequest` (add `p."BrandID" = @BrandID`), and `GetProductsByIDSpec` (add the brand predicate). Fix the duplicated reference-check queries in `DeleteProductsSpecRequest.cs:84-118` while touching the file.
- **`ForceDeleteProductSpecRequest` rewrite**: parameterized SQL, every statement scoped to the active brand (`DistributorAPLs` via brand-scoped UPC resolution, `MarketOverviews`/`TradeSpend*` via brand-checked product ids), wrapped in one transaction (today `QueryMultipleAsync` runs the 7 statements with no transaction, `:92`). Product decision on whether the cascade survives at all: Q4.
- **Demand() call sites** (payload-dependent): `UpsertProductSpecRequest` (`request.ID is null ? Create : Edit`), `UpsertPriceListRequest` (same; the ValidFrom fork stays under Edit), `UpsertCategoryRequest` (same). `CreatePriceListRequest` is create-only → plain attribute Create, no Demand.
- **Helpers/files to delete**: none owned by this area. `BrandValidationMiddleware` (shared) is retired per plan 4.4 — but because the header check is the **only** guard on all 28 attribute-free rows, this area must gain `[RequireModule]` in the same deploy that retires it, or the deletes/upserts become anonymous-authenticated writes.
- **BrandID-header edge cases**: web always sends the header from the active brand route; the admin app throws client-side on a malformed brand before sending (`crmDataUpload.helper.ts:36-43`) and relies on the ADMIN bypass → wire the support context before the flip. Missing header: brand workspace defaults to the organization id (arch §6.1); `Guid.Empty` stamping must become impossible.
- **Transactions**: product upsert writes spec + bulk price lists + bulk soft-deletes without a transaction (`UpsertProductSpecRequest.cs:131-176`) and force-delete's cascade is non-transactional — fold into the rewrite above; imports use bulk ops per batch (acceptable as-is).

## 7. FE impact (Phase 5)

Web (caboodle.web, develop @ 956295e4), gating per `_inventory.md` Section C:

- `/categories`, `/products`, `/pricing` (route group `src/app/(brand)/[brandID]/(product-specs)/`) → slug `categories-products-pricing`; nav "Management → Product Specs" → `/{brandId}/categories`, same slug. - **Sub-user veneer → real grants.** The three tables' negative role checks (§5 anchors) are the only "permission UI" today. When `/me/access` lands, editability should derive from the action flags on the active brand's module map (`modules["product-spec"]` contains `create`/`edit`/`delete`/`export`), not from the role string — that makes the veneer honest for Custom users and removes `useRoleStore` from these components. - **Q1 wrinkle**: FE route gating uses the child `categories-products-pricing`, the API will gate on parent `product-spec`. Under invariant 5 a child grant always implies the parent, so route-gated users always pass the API; the reverse (parent without child) hides the screens but leaves the API reachable — acceptable, document in the grant-editor UX.
- **403 handling**: `BulkUploader` posts with plain `axios`, not the intercepted instance (`src/components/shared-components/bulkUploader.helpers.ts:94-110`) — fine for the 403-never-401 contract, but new module-denied 403s must render as permission errors, not "network error". ## 9. Open questions

1. **Q1 — Parent or child slug for the API?** The FE gates routes on the child `categories-products-pricing`; the Broker audience has only the `product-spec` copy; all nine dependency seeds and the arch §6.3 Upsert example point at the parent `product-spec`; Required-dependency View lands on the parent. Recommendation: gate all API rows on `product-spec` in both audiences (as written in §4); keep `categories-products-pricing` as the FE-navigation child and have the grant editor write catalog actions to the parent (a child grant without parent actions is a UI-only state). Alternative — gate brand rows on the child — breaks dependency-View for every promo/report consumer and needs new seeds; not recommended.
2. **Q2 — Sub-user write parity.** BRANDSUBUSER/BROKERSUBUSER are read-only **in the UI only** (§5); the server has always accepted their writes. Recommendation: migrate them at `Full` (consistent with D2 and arch §10.1) and treat the veneer as a UI bug the new model supersedes; if product wants the read-only intent made real, seed those memberships as `Custom` with `product-spec: view` instead — a deliberate tightening the comparator must whitelist.
3. **Q3 — Should brokers write brand master data at all?** Under D1 + Full, any brokerage with the `product-spec` copy enabled gets Create/Edit/Delete/Export on every connected brand's catalog — which matches today's server behavior and the FE's primary-broker edit UI. If product wants brokers read-only here, set the Broker copy's `Modules.AvailableActions` to View (the N11 flags column) rather than inventing a guard asymmetry. Needs Platform-Admin sign-off; default is parity (keep writes).
4. **Q4 — What happens to force-delete?** It is a live web-FE surface (`product.service.ts:167`) but behaves like a platform data-cleanup tool (cross-tenant hard-delete cascade). Recommendation: keep the endpoint brand-facing at `Delete`, rewrite it brand-scoped/parameterized/transactional (§6), and drop the cross-brand `DistributorAPLs`-by-UPC reach — brokerage APL cleanup belongs to the APL area (workbook 01, Q7). Alternative: move it behind `[MustHavePermission]` and give the FE a support-ticket path; needs product confirmation on who may hard-delete.
5. **Q5 — Which slug gates `GET productspecs/for-bannerSku/{bannerID}`?** It exists solely for the Banner SKU screens, which gate on `distributors` (brand `banners` route) and have no catalog dependency on `product-spec`. Recommendation: `RM(brand: "distributors", View)` (as written in §4.1), omitting the broker audience (no broker surface calls it, §5-8). Alternative: keep `product-spec` and seed `distributors → product-spec (Required)` — heavier, grants more than the screen needs.
